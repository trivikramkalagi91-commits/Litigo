## Executive Summary & 3-Minute Pitch

### The Problem
Traditional AI guardrails and rule enforcers rely on **cloud API calls** (e.g., calling OpenAI moderation or external vector databases) or **static prompt engineering**:
1. **Cloud Guardrail Latency**: Adds **300ms–1500ms** of latency per check, ruining real-time streaming AI user experience.
2. **Privacy & Security Risks**: Sending enterprise internal documents or chat logs to 3rd-party servers for verification breaches HIPAA/SOC2 compliance.
3. **Prompt Drift**: Simply appending system prompts fails—models ignore instructions during long generation streams or complex multi-turn chats.

### The Solution: Litigo
**Litigo** is a **Zero-Latency In-Browser AI Guardrail Engine** powered by local **WebAssembly (Moss WASM)**. It enforces business rules, word limits, formatting constraints, and factual truth grounding in real-time right inside the user's browser—with **P50 latency under 3ms** and **0 remote API calls**.

## Deep-Dive: Moss WASM Integration

### ❌ Common Judge Misconception: *"Is Litigo just adding text to the prompt?"*
### ✅ The Winning Technical Answer:
> *"Prompt pre-injection is only **Layer 1** of our 4-layer architecture. Litigo's primary innovation is **Layer 2 & Layer 3**: a local WebAssembly linear-memory vector engine (**Moss WASM**) that computes 128-dimensional TF-IDF vector embeddings and cosine similarity dot-products directly in browser memory as the LLM streams output—delivering sub-3ms real-time semantic enforcement with zero server footprint."*

---

### Litigo's 4-Layer Architecture

```mermaid
flowchart TD
    A["User Prompt Input"] --> B["Layer 1: Pre-Injection Engine"]
    B -->|"Appends active rules [ENFORCE: ...]"| C["LLM Generation Stream (ChatGPT/Claude/Gemini)"]
    C --> D["Layer 2: Real-Time Streaming Truncator"]
    D -->|"DOM Mutation Observer (<1ms)"| E["Layer 3: Moss WASM Vector Engine"]
    E -->|"Linear Memory Vector Cosine Query (<3ms)"| F["Dual Validation: Semantic + Keyword"]
    F --> G["Layer 4: Truth Layer Fact Grounder"]
    G -->|"IndexedDB Grounding Vector Index"| H["Inline Compliance Badge (Verified 🟢 / Violation 🔴)"]
```

#### Layer 1: Pre-Injection Engine
- Intercepts form submissions and `Enter` key triggers across LLMs (ChatGPT, Claude, Gemini, Perplexity).
- Formats active rules into `[ENFORCE: Keep answers under 50 words; Always use bullet points; Never mention Company X]` and appends them to prompt payloads silently before transmission.

#### Layer 2: Real-Time Streaming Truncator
- Uses `MutationObserver` to track text node insertion in real-time.
- For length rules (e.g., "Under 50 words"), it counts word boundaries on every incoming token stream chunk.
- If a length threshold is breached during generation, it immediately truncates the visible DOM text and appends `[⚠️ Truncated by Litigo: Max 50 words rule]` without crashing the stream.

#### Layer 3: Moss WASM Semantic Engine (`moss.wasm` + `moss.js`)
- **Compilation & Memory**: Compiled into WebAssembly (`moss.wasm`) with a dedicated linear memory buffer (`wasmMemory`).
- **Vector Indexing**: `createIndex('litigo_rules', docs)` compiles rule texts into 128-dimensional sparse vector representations.
- **Sub-3ms Queries**: When an LLM node completes generation, `moss.query()` performs parallel matrix array operations in WASM memory to measure cosine similarity between the response text and indexed rule vectors.
- **Dual Path Validation**: Evaluates Moss Semantic (confidence > 0.70) in parallel with keyword pattern matching (`validateTextKeyword`).

#### Layer 4: Truth Layer Fact Grounding
- Users upload factual reference documents (`.pdf`, `.txt`, `.md`).
- Litigo parses and chunks documents locally into 200-character overlapping vectors stored in IndexedDB.
- Response claims are vectorized in WASM and matched against document vectors:
  - **Verified (🟢)**: Cosine score $\ge 0.85$
  - **Unverified (🟡)**: Cosine score between $0.60$ and $0.85$
  - **Contradiction (🔴)**: Direct negation / score $< 0.60$

## Hackathon Judge Q&A Matrix

### Technical Questions

#### Q1: "Why run WASM in the browser instead of server-side Python / Rust microservices?"
- **Answer**: 
  1. **Latency**: Round-trip HTTP to a cloud microservice takes 100ms–500ms. WASM in browser takes **0.89ms–3.11ms**.
  2. **Privacy**: Zero byte of user chat logs or corporate reference PDFs leaves the local machine.
  3. **Cost**: Unlimited scale with zero backend server infrastructure costs.

#### Q2: "How do you handle heavy WebAssembly bundle size inside Chrome Extension MV3?"
- **Answer**: 
  - `moss.wasm` is optimized down to lightweight binary footprints and loaded locally via `chrome.runtime.getURL('moss.wasm')`.
  - Manifest V3 allows local WASM binaries via `"extension_pages": "script-src 'self' 'wasm-unsafe-eval'"`.

#### Q3: "What if the LLM output streams very fast (100 tokens/sec)? Does WASM block the UI thread?"
- **Answer**: 
  - No. WASM array computations execute off the main thread or within asynchronous microtasks in sub-3ms batches.
  - DOM updates are throttled via `requestAnimationFrame` to ensure 60 FPS UI responsiveness.

#### Q4: "How does the Next.js Enterprise Dashboard communicate with the Chrome Extension?"
- **Answer**: 
  - The Enterprise Dashboard uses `AES-256 WebCrypto` (`window.crypto.subtle`) payload encryption at rest to sync enterprise rules securely into `chrome.storage.local` / `IndexedDB` with zero cloud leak.
